1. Función de MySQL en la arquitectura híbrida

MySQL es la fuente de verdad operativa del prototipo: guarda toda la información académica detallada y los datos necesarios para operar el sistema. Hyperledger Fabric no almacena esos datos; solo guarda una huella criptográfica (HMAC) de cada versión de un registro. MySQL también conserva el vínculo con la blockchain (evidenceId, TX_ID, número de bloque) y la bitácora de trazabilidad. Esta separación permite consultar y corregir datos con las capacidades de una base relacional, y a la vez demostrar su integridad contra un ledger inmutable y replicado.

             ├─ teacher ──────────┤              │                   ├─ blockchain_evidence

  • Claves primarias: 18, todas INT AUTO_INCREMENT, salvo student_identity, cuya PK es la FK student_id (relación 1:1).
  • Claves foráneas: 22. Por defecto ON DELETE RESTRICT (no se puede borrar un estudiante con matrículas ni un registro con evidencias); student_identity usa CASCADE y app_user.teacher_id usa SET NULL.
  • Unicidad (25 índices únicos): códigos de negocio (academic_result.code, student.pseudonym_code, blockchain_evidence.evidence_id, tx_id…), un resultado por matrícula y actividad (enrollment_id, activity_id), una matrícula por estudiante y año, una evidencia por resultado y versión (result_id, version).
  • Índices de consulta (8): por actividad, sección, periodo, docente, estado de la evidencia y (result_id, occurred_at) para la trazabilidad.
  • Dominios cerrados: ENUM para calificación (AD/A/B/C), tipo de actividad, asistencia, tipo y estado de evento; DECIMAL(4,2) para la nota; DATETIME(3) para las marcas de tiempo que se firman.

El repositorio que carga un registro para firmarlo (ACADEMIC_RECORD_INCLUDE) no incluye student_identity, y ninguna de las vistas la expone. Los datos del seed son ficticios: los documentos usan el tipo COD-VAL (VAL-0001…) para que no puedan confundirse con un DNI real, y no se presentan como información oficial de la institución.

7. Interacción con Prisma

schema.prisma es la fuente de verdad del modelo. prisma migrate genera la migración SQL y database/schema.sql se deriva de ella, por lo que ambos son idénticos. El cliente Prisma se instancia una sola vez (lib/db/prisma.ts, marcado server-only) y solo los repositorios lo usan:

TraceabilityService → AcademicRecordRepository.findByCode()        → prisma.academicResult.findUnique({ include })
                    → BlockchainEvidenceRepository.savePending()    → prisma.blockchainEvidence.upsert()
                    → BlockchainEvidenceRepository.markConfirmed()  → prisma.blockchainEvidence.update()
                    → TraceabilityEventRepository.create()          → prisma.traceabilityEvent.create()
                    → AcademicRecordRepository.rectify()            → prisma.$transaction(historial + versión+1)

7.1 Coherencia entre los scripts SQL y Prisma

Se creó una base nueva usando solo schema.sql, seed.sql y views.sql (sin Prisma) y se verificó REG-000001 contra el ledger. El HMAC calculado sobre esa base es idéntico al anclado en Fabric: el esquema y los datos SQL son exactamente equivalentes a los de Prisma.

8. Respaldo y recuperación

  • Respaldo: database/backup.sh ejecuta mysqldump --single-transaction --routines --triggers (copia consistente sin bloquear InnoDB) hacia database/backups/.
  • Recuperación: database/restore.sh <archivo>. Después se ejecuta npm run verify: la blockchain permite comprobar que los datos restaurados son los originales.
  • Persistencia: volumen Docker mysql_data; los datos sobreviven a reinicios del contenedor (PT-15).

Prueba realizada: respaldo → DROP DATABASE (pérdida total) → restauración → verificación.
