1. Objetivo

Instalar las dependencias y desplegar una red Hyperledger Fabric funcional y reproducible sobre la que el prototipo realice sus primeras operaciones: levantar la red, crear el canal, unir los peers, desplegar el chaincode, consultar su estado, detener la red y limpiar la infraestructura con comandos simples.

3. Arquitectura desplegada

Se optó por una red construida desde cero (no por la test-network de fabric-samples) para controlar los nombres de organizaciones, MSP, canal y chaincode exigidos por el proyecto. Se usa el modelo de Fabric 2.5 sin canal de sistema: el orderer se une al canal mediante la API de participación de canales (osnadmin). El chaincode se ejecuta como servicio externo (Chaincode-as-a-Service), de modo que el peer no necesita acceso al socket de Docker; esto hace la red portable entre Windows, Linux y macOS.

4. Requisitos

  • Docker Desktop (Windows/macOS) o Docker Engine (Linux) en ejecución; ~4 GB libres para imágenes.
  • Bash: en Windows, Git Bash. Los scripts exportan MSYS_NO_PATHCONV=1 y convierten rutas con pwd -W.
  • Puertos libres: 7050, 7053, 9443 (orderer); 7051, 9444, 9051, 9445 (peers); 7054, 8054 (CAs).
  • No se requieren los binarios de Fabric en el host: cryptogen, configtxgen, osnadmin y peer se ejecutan dentro del contenedor cli (imagen fabric-tools).

5. Instalación

  1. Instalar e iniciar Docker. Verificar con docker info.
  2. Descargar las imágenes (lo hace Compose automáticamente la primera vez): docker pull hyperledger/fabric-peer:2.5 hyperledger/fabric-orderer:2.5 hyperledger/fabric-tools:2.5 hyperledger/fabric-ca:1.5 node:20-alpine.
  3. Instalar las dependencias del chaincode: cd chaincode/academic-traceability && npm install.
  4. Ejecutar los scripts de la sección 8.

7.1 Peer (fragmento)

Cada peer habilita TLS, se anuncia por gossip con su nombre DNS interno, usa LevelDB con base de historial y deshabilita el acceso a Docker (CORE_VM_ENDPOINT=) porque el chaincode corre como servicio.

8. Comandos

ComandoAcción
./scripts/network.sh upgenera identidades si faltan y levanta orderer, peers, CAs, cli (y el chaincode si ya fue desplegado)

9. Explicación de cada servicio

ServicioRol
orderer.example.comServicio de ordenamiento (Raft, un nodo). Recibe transacciones ya endosadas, las ordena, forma bloques (máx. 10 tx o 2 s) y los distribuye. No ejecuta chaincode.
peer0.nuevohorizonte.example.comPeer de la I.E. Nuevo Horizonte. Endosa (simula el chaincode y firma), valida bloques y mantiene su copia del ledger. Expone el servicio Gateway que usa la aplicación.
peer0.validator.example.comPeer de la organización de validación. Segundo endosante requerido por la política y réplica independiente del ledger.
ca.nuevohorizonte / ca.validatorFabric CA de cada organización, operando con la CA raíz generada por cryptogen, para registrar nuevas identidades en fases posteriores (usuarios por rol).
academic-traceability-ccProceso del chaincode (Node 20). Los peers se conectan a él en :9999 para ejecutar las funciones del contrato.
cliHerramientas de administración: generación de identidades, bloque génesis, unión al canal y ciclo de vida del chaincode.
