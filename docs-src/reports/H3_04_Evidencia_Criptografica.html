1. Propósito

El compromiso criptográfico es el puente entre ambos mundos: un valor corto calculado a partir del registro académico almacenado en MySQL que se ancla en Hyperledger Fabric. Si alguien modifica el registro después de anclarlo, al recalcular el compromiso el valor ya no coincide con el del ledger y la alteración queda al descubierto (RNF-13). El módulo está en app-next/src/lib/crypto/ y usa exclusivamente node:crypto.

La técnica viene fijada por el Hito 2: «calcular un HMAC-SHA-256 sobre una representación canónica del registro. La clave secreta permanece en el middleware y nunca se escribe en el ledger» (H2-03 §4). También lo exigen los requisitos RF-13 y RNF-21 (serialización determinista) y la regla RN-04 (mismo conjunto y orden de campos para un mismo estado).

2. SHA-256

SHA-256 es una función hash criptográfica de la familia SHA-2 (FIPS 180-4). Transforma una entrada de cualquier tamaño en 256 bits (64 caracteres hexadecimales) con tres propiedades: es determinista, resistente a preimagen (no se puede obtener la entrada a partir del resumen) y resistente a colisiones. Además presenta efecto avalancha: un cambio mínimo en la entrada altera aproximadamente la mitad de los bits de la salida.

3. HMAC

HMAC (RFC 2104) es un código de autenticación de mensajes que combina una función hash con una clave secreta: HMAC(K, m) = H((K ⊕ opad) ‖ H((K ⊕ ipad) ‖ m)). Con H = SHA-256 se obtiene HMAC-SHA-256, de 256 bits. Solo quien conoce la clave puede calcular o verificar el valor.

4. Diferencia y razón de elegir HMAC

El motivo decisivo es la privacidad, como advierte H2-03: con un hash directo, «la evidencia On-chain equivaldría a aplicar un hash sobre datos potencialmente identificables». En el dataset del Hito 2 las notas son enteros de 0 a 20: con un SHA-256 simple, cualquier miembro del canal podría probar los 21 valores posibles hasta dar con el hash publicado y así descubrir la nota. La sección 8 lo demuestra sobre REG-0001.

6. Algoritmo

generateEvidence(record):
  1. input     ← proyección del resultado al payload canónico (AcademicRecordService)
  2. validado  ← AcademicRecordSchema.parse(input)                    // Zod
  3. canónico  ← JSON con orden fijo y normalización (sección 5)
  4. compromiso ← HMAC-SHA-256(clave = process.env.HMAC_SECRET, mensaje = UTF-8(canónico)) en hexadecimal
  5. devolver { evidence: compromiso, algorithm: "HMAC-SHA-256", canonicalVersion: "2" }

verifyEvidence(record, compromisoReferencia):
  1. calculado ← generateEvidence(record).evidence
  2. valid     ← timingSafeEqual(hex(referencia), hex(calculado))    // tiempo constante

Encadenamiento (H2-03 «compromiso anterior»): la versión n se ancla con previousCommitment = compromiso(n-1).

7. Seguridad

  • Gestión de la clave: HMAC_SECRET se lee de la variable de entorno y se valida (mínimo 32 caracteres; se usan 64 hexadecimales = 256 bits generados con crypto.randomBytes). Nunca se escribe en el código, en el repositorio ni en los logs.
  • Clave independiente de la tokenización: los tokens del Hito 2 también son HMAC truncados, pero con otra clave que no forma parte del prototipo. Conocer HMAC_SECRET no permite revertir tokens.
  • Custodia: quien verifica necesita la clave; todo el equipo debe usar la misma. Si se pierde, las evidencias existentes ya no pueden verificarse. Para producción: gestor de secretos y procedimiento de rotación (nueva canonicalVersion y re-anclaje).
  • Comparación en tiempo constante (timingSafeEqual).
  • Límite conocido: el HMAC prueba que los datos no cambiaron desde que se anclaron, no que fueran correctos al registrarse. Eso depende del control de acceso (Hito 5).

  • Determinismo: 1000 cálculos dan un único valor; el orden de las propiedades no influye.
  • Avalancha: cambiar el puntaje en 0,01 altera 130 de 256 bits (≈ 51 %).
  • Privacidad: con SHA-256 sin clave, la nota (20.00) se descubre en como máximo 21 intentos; con HMAC no puede deducirse sin la clave.
