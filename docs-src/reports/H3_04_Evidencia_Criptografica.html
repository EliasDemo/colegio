1. Propósito

La evidencia criptográfica es el puente entre ambos mundos: un valor corto, calculado a partir del registro académico almacenado en MySQL, que se ancla en Hyperledger Fabric. Si alguien modifica el registro después de anclarlo, al recalcular la evidencia el valor ya no coincide con el del ledger y la alteración queda al descubierto. El módulo está en app-next/src/lib/crypto/ y usa exclusivamente node:crypto.

2. SHA-256

SHA-256 es una función hash criptográfica de la familia SHA-2 (FIPS 180-4). Transforma una entrada de cualquier tamaño en 256 bits (64 caracteres hexadecimales) con tres propiedades: es determinista, es resistente a preimagen (no se puede obtener la entrada a partir del resumen) y es resistente a colisiones (es inviable hallar dos entradas con el mismo resumen). Además presenta efecto avalancha: un cambio mínimo en la entrada cambia aproximadamente la mitad de los bits de la salida.

3. HMAC

HMAC (RFC 2104) es un código de autenticación de mensajes construido sobre una función hash y una clave secreta: HMAC(K, m) = H((K ⊕ opad) ‖ H((K ⊕ ipad) ‖ m)). Con H = SHA-256 se obtiene HMAC-SHA-256, también de 256 bits. Solo quien conoce la clave puede calcular o verificar el valor.

4. Diferencia y razón de elegir HMAC

AspectoSHA-256HMAC-SHA-256
ClaveNo usaUsa HMAC_SECRET (256 bits aleatorios)
Quién puede calcularloCualquieraSolo quien tiene la clave
GarantíaIntegridadIntegridad y autenticidad del origen
Riesgo con datos de dominio pequeñoAlto: se puede adivinar la entrada probando todas las opcionesNulo sin la clave

El factor decisivo es la privacidad. Un registro académico tiene pocas combinaciones posibles: las referencias (REG, EST-PSE, ACT…) siguen un formato conocido y la nota solo puede tomar unos pocos valores (0 a 20 y AD/A/B/C). El ledger es visible para todos los miembros del canal, así que con un SHA-256 simple cualquiera de ellos podría probar todas las notas hasta dar con el hash publicado y así descubrir la nota, lo que convertiría la evidencia en una fuga de datos. Con HMAC esto no es posible sin la clave. La sección 8 lo demuestra sobre un registro real.

5. Canonicalización

El HMAC opera sobre bytes; para que la misma información produzca siempre exactamente los mismos bytes se define una forma canónica (canonicalizeAcademicRecord(), versión 1). No se usa JSON.stringify() directamente sobre el objeto, porque su salida depende del orden en que se crearon las propiedades.

ReglaDefinición
Orden de camposFijo: canonicalVersion, academicRecordId, studentReference, enrollmentReference, sectionReference, subjectReference, activityReference, periodReference, teacherReference, qualitativeGrade, numericScore, observation, recordedAt, version
CodificaciónUTF-8; textos normalizados a Unicode NFC (una “ñ” compuesta o descompuesta produce los mismos bytes)
EspaciosSe recortan al inicio y al final y los espacios internos se colapsan a uno; JSON compacto, sin espacios entre elementos
MayúsculasLos códigos técnicos se convierten a MAYÚSCULAS; la observación conserva su texto
NúmerosnumericScore como cadena con exactamente 2 decimales ("19.50"): evita que 19.5 y 19.50 difieran y los errores de coma flotante
FechasISO 8601 en UTC con milisegundos (2026-06-10T20:20:00.000Z); las fechas con zona horaria se convierten a UTC
nullExplícito: el campo nunca se omite; una observación vacía equivale a null
Validación previaEsquema Zod AcademicRecordSchema: si un campo no es una referencia seudónima válida, se rechaza antes de calcular
Versión del formatocanonicalVersion se incluye en la entrada: un cambio futuro de reglas no se confunde con el formato actual

La entrada contiene solo referencias seudónimas y el resultado; nunca nombres ni documentos. La version del registro forma parte de la entrada: cambiar la versión sin una rectificación anclada también se detecta.

6. Algoritmo

generateEvidence(record):
  1. input     ← proyección del registro a referencias seudónimas (AcademicRecordService)
  2. validado  ← AcademicRecordSchema.parse(input)                   // Zod
  3. canónico  ← JSON con orden fijo y normalización (sección 5)
  4. evidence  ← HMAC-SHA-256(clave = process.env.HMAC_SECRET, mensaje = UTF-8(canónico)) en hexadecimal
  5. devolver { evidence, algorithm: "HMAC-SHA-256", canonicalVersion: "1" }

verifyEvidence(record, evidenceReferencia):
  1. calculada ← generateEvidence(record).evidence
  2. valid     ← timingSafeEqual(hex(evidenceReferencia), hex(calculada))   // tiempo constante
  3. devolver { valid, computedEvidence: calculada }

evidenceId = "EVD-" + código + "-V" + versión        (p. ej. EVD-REG-000001-V1)

7. Seguridad

  • Gestión de la clave: HMAC_SECRET se lee de la variable de entorno y se valida (mínimo 32 caracteres; se usan 64 hexadecimales = 256 bits generados con crypto.randomBytes). Nunca se escribe en el código, en el repositorio (.env está en .gitignore) ni en los logs (el logger redacta los campos cuyo nombre contiene secret o key).
  • Custodia: quien verifica necesita la clave. Todo el equipo debe usar la misma; si se pierde, las evidencias existentes ya no pueden verificarse. Para producción se recomienda guardarla en un gestor de secretos y definir un procedimiento de rotación (nueva versión canónica y re-anclaje).
  • Comparación en tiempo constante (timingSafeEqual): evita filtrar por tiempos de respuesta cuántos caracteres coinciden.
  • Privacidad On-chain: el ledger solo recibe el HMAC; ni la nota ni el seudónimo del estudiante viajan a Fabric (ver H3-05, verificación de los 20 bloques).
  • Límite conocido: HMAC prueba que los datos no cambiaron desde que se anclaron; no prueba que fueran correctos al registrarse. Eso depende de los controles de acceso (Hito 5).
